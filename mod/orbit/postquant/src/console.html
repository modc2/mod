POSTQUANT

a key/value market where every byte pays rent

ML-DSA (FIPS 204) · SLH-DSA (FIPS 205) · SHA3-256 · wasm-verified witnesses · no elliptic curves · client-side encrypted vault · v0.12
READ AS same paper, two voices

A post-quantum L1 whose entire state machine is a market in key/value space. There is one thing to own on this chain — a key in the store — and the whole protocol is the market for it: write gas per byte, witness gas per byte of signature, and rent per byte-hour against a prepaid escrow. Every signature is lattice or hash-based, every commitment is a hash, nothing in the trust path is an elliptic curve — and every witness is checked by the wasm module that is its key type. Data lives off-chain in a vault that encrypts on the client before any node sees it, and smart contracts are stored as content-addressed code behind owned, rent-paying keys.

This is a small blockchain with one idea. The only thing you can own on it is an entry on a public board — a name and what it says — and keeping it there costs a little, like renting a mailbox. Every signature is built to survive quantum computers: no elliptic curves anywhere. Your files are locked on your own device before they're stored, so the computers keeping them can't read them. If any of this page loses you, the ? helper in the corner will explain.

0Why this design

There are three questions to ask of any chain that wants to still be trustworthy in twenty years. Will a quantum computer open your lock? If one kind of lock is broken tomorrow, are you stuck? Who pays for the data everyone has to keep forever? Most chains answer the first with "we'll upgrade later", the second with a hard fork, and the third by not charging for it. This chain answers all three in its rules, today — and the figures below are drawn from this running node, not from a slide.

A long-lived ledger has to survive three failures that current designs leave open: (i) Shor's algorithm against every curve signature, (ii) a cryptanalytic break of whichever single post-quantum family a chain standardises on, and (iii) unpriced state growth that makes every node's disk a commons. The design choices here are the minimal set that closes all three at once: two unrelated signature families plus a third Cairo-verified hash wall (closes i and ii), key types as hash-pinned wasm so a new family is a plugin and not a fork (closes ii going forward), and write gas + witness gas + rent priced per byte (closes iii). Off-chain data goes to a vault that encrypts on the client (5e), and contracts are stored as content-addressed code (5f), so the chain only ever holds 32-byte commitments.

1No curves

Most blockchains guard your money with a kind of math — elliptic curves — that a big enough quantum computer is expected to break outright. This chain simply never uses it. Your wallet locks with one of two completely different mechanisms instead: one built on lattice problems, one built on nothing but hashing. They share no weakness, so if one ever falls, the other still holds — and a third, Cairo-checked SHA-256 lock (section 5d) can be stacked on top.

You choose your lock when you create a wallet, and your address is permanently stamped with the choice — a signature made for one kind of lock can never be replayed against another.

Signatures on this chain come from two families that share nothing: ML-DSA (FIPS 204, module lattices) and SLH-DSA (FIPS 205, nothing but SHAKE256). If lattices fall, a hash-based witness still stands. Key exchange is ML-KEM (FIPS 203), and every commitment — addresses, transaction ids, Merkle roots, state roots — is SHA3-256. Nothing here is ed25519 or secp256k1, because a curve is exactly the thing Shor's algorithm takes apart.

What survives a quantum adversary is lattices and hashes. Grover's algorithm halves the exponent of a hash search, so 256 bits stays an effective 128 — a square-root loss the parameter sizes already absorb. Every scheme is implemented from the FIPS specifications in pure python under pq/, with no dependencies.

An account picks its key type at creation and its address commits to the choice: pq + the first 20 bytes of domain-separated SHA3-256 over the algorithm's domain and the public key, so the same bytes arriving under two schemes are two different addresses and a signature can never be replayed across key types. The first transaction from an address carries its public key inline; every later one does not.

1bThe wasm is the algorithm

Each kind of lock ships as a small sealed program with a fingerprint of its exact bytes on file. When a transaction arrives, the chain checks the signature inside that very program — and refuses to run one whose fingerprint doesn't match. Adding a new kind of lock later means dropping in one file, not rewriting the chain.

New lock designs aren't banned for being old-fashioned, either — they're priced: anything that would take longer than a published floor to break may play, and the catalog says plainly what a quantum computer would do to each one.

A key type here is not a branch in the node's code — it is a compiled wasm verifier plus the SHA3-256 of its bytes, registered in a manifest. Every transaction the chain accepts has its witness checked inside the wasm module registered for its key's algorithm; the node refuses to run a blob whose hash does not match the registry, and refuses the witness outright if the module cannot run. What it means for a signature to be valid is thereby pinned to exact bytes any node can hash, ship and re-run.

That is also what makes the key-type set amendable: a future algorithm arrives as one plugin file that registers keygen/sign plus a verifier blob and its declared hash — in pq/algos.d/ in-tree or ~/.mod/postquant/algos/ per node — with no change to the chain. The gate prices instead of prohibiting: a classical algorithm registers, appears in the catalog with its measured break cost, and witnesses if that cost clears the floor — refused only below it, or when the entropy probe catches the keyspace lying. The builtin verifiers are ~600 lines of dependency-free Rust each, compiled with bare rustc, with parity tests against the python references (pq/wasm-src/).

2One thing to own

Think of the chain as a public notice board. You own a spot on the board — a name — and what it says. Usually you don't post the document itself, just its fingerprint, so anyone can later check "yes, this is exactly that file" without the chain ever storing it. Keeping your spot costs money for as long as you keep it — and that bill, in three parts, is the whole protocol.

A key maps to a value. The value is bytes, and is usually a 32-byte SHA3-256 digest of something kept off-chain — the chain stores the commitment, never the data. Holding that pair costs money for as long as you hold it, and that cost structure is the entire protocol.

3Three prices, separate on purpose

  • A posting fee — paid once, per byte you write. Names cost more than contents, because every computer in the network has to index a name forever.
  • A signature fee — quantum-safe signatures are big (thousands of bytes, not dozens), and each wallet pays for exactly the bytes its kind of lock produces. Nobody gets quietly subsidised.
  • Rent — a small hourly charge per byte, drawn from a deposit you top up. When the deposit runs dry your entry expires, and anyone may clear it away and keep your cleanup bond — which is why expiry actually happens. Remove it yourself and the bond comes back.
  • Write gas — one-time, per byte entering the state. A key byte costs 4x a value byte, because a key is an index entry the whole network sorts forever. A value declared kind=hash is cheaper still: the chain prices commitments below blobs, out loud.
  • Witness gas — per byte of signature and public key. An ML-DSA-44 signature is 2420 bytes against ed25519's 64, and an SLH-DSA-SHAKE-128f one is 17088 — the honest price of resting on nothing but hashes. A chain that charges a flat 21000 for a transfer is quietly subsidising its own witnesses; this one bills each key type for exactly the bytes it puts on the wire.
  • Rent — per byte per hour against a prepaid escrow. When the escrow runs dry the entry expires, and anyone may sweep it for the bond the writer put up — which is what makes expiry real rather than advisory. Delete the entry yourself and the bond comes back whole.

4The fee market

When people write a lot, writing gets more expensive; when it's quiet, it gets cheaper — automatically, a little every block, aimed at a steady few kilobytes of growth. The fee is destroyed rather than pocketed, so nobody profits from congestion.

Write gas settles at a base fee that floats with state growth — EIP-1559 over bytes, not execution. The scarce resource metered is every node's disk forever: the target is 4096 bytes of state growth per block, and the base fee moves ±12.5% per block against it. If the store grows faster than target, writing gets more expensive until it stops. The base fee is burned; the tip goes to the proposer.

5The market for keys

Names can be put up for sale and bought. The buyer gets the entry with its remaining rent deposit and bond included — like buying a domain name that comes pre-paid. Readable names are the point: you can't bid on something you can't say.

Keys can be listed and bought. The buyer takes the entry with its remaining lease and bond — a well-funded key is worth more than an empty one. Human-readable keys are the point of a namespace market: you cannot bid on something you cannot say.

5bBuild your own lock

You can snap existing locks together into a new one. ALL-OF means every lock has to open — a thief has to break all of them. ANY-OF means any one opens it (handy, but only as strong as the weakest). THRESHOLD means "any 2 of these 3", like a bank vault with three keyholders. The new lock is tested live before it's allowed in, and you can sign your name to it on the chain.

Composite key types (pq/compose.py) are built from registered ones: all concatenates public keys and signatures and verifies every part — classical cost is the max over parts and it is quantum-safe if any part is; any carries a one-byte index and one part's signature — it falls at the weakest; threshold k carries a k-bit bitmap and falls when the k weakest fall. Sub-seeds are SHAKE-split per (composite, slot, part), so a part key never equals a bare wallet's. Parts may be composites, so key types form a DAG; names never rebind, so it stays acyclic. The gate probes the composed keygen like any plugin, and pq_keytype_test runs a refutation-only battery (roundtrip, tamper, truncation, context and key binding, per-part ablation). publish=true anchors keytype/<name> = SHA3(spec) from the author's wallet, so authorship is a key you can list and sell.

5cPrivate locks

A normal account tells the world which kind of lock it uses the first time it signs — which tells an attacker exactly what to attack. A private account never does: every signature it makes is sealed in an identical-looking 64 KB envelope, so a lattice lock, a hash lock and a Cairo lock all look like the same noise. In the builder, tick make it private and the lock you just built is hidden inside a new private wallet.

The private key type commits the address to SHA3(inner, salt, inner_pk); a witness is an ML-KEM-768 envelope over (inner, salt, pk, sig), padded to one fixed size, that only the proposer opens — it checks the commitment, runs the gate on the inner scheme and runs that scheme's verifier. The anonymity set is every accepted key type that fits the envelope, composites included, so the attacker never learns which problem to attack and never sees a public key to start from. Trust, stated plainly: the proposer can see the scheme; if the seal key leaks, each account falls back to its inner scheme's own card. pq_keytype create private=true forges and hides in one step.

5dCairo: one more wall

Every extra lock in an ALL-OF stack only helps if it's a different kind of lock — two copies of the same lock fall to the same trick. So this chain adds a third kind, built on plain SHA-256 hashing, whose checking program is written in Cairo — the language behind STARK proofs, which are themselves made of hashes and so stay quantum-proof. The QUANTUM-HARD PRESET in the builder stacks lattice + hash + Cairo: a quantum computer has to beat all three, and no single breakthrough does it.

CAIRO-MSS-SHA256 (pq/cairomss.py) is a SPHINCS-shaped hypertree without FORS: four layers of 6-high Merkle trees of WOTS keys (n=32, w=16, 67 chains, 224 leaves), tweakable hash T = SHA-256(pub_seed | address | data), 64-byte public key, 9376-byte signature. It rests on SHA-256 preimage/second-preimage resistance alone — an assumption independent of ML-DSA's module lattices and SLH-DSA's SHAKE256 — so in an all composite a forger needs a lattice break and a SHA-256 inversion (Grover: ~2128). Its verifier is a Cairo 2 program (pq/cairo/src/lib.cairo, every input whole u32 words through core::sha256); pq_cairo check runs a witness in the Cairo VM and reports parity with the Python verifier the hot path uses (~1.5 s in the VM vs ~10 ms in Python). Because a Cairo execution is exactly what a STARK proves, this is the route by which a hidden witness could one day be verified by a hash-based proof instead of the proposer's word — this node ships the verifier, not a prover. Honest limit: the leaf is chosen by the message hash, so one-time key reuse has odds ~q2/225 after q signatures — it is a layer, not a solo wallet for heavy use.

5eThe vault: encrypted before it leaves you

The chain only stores fingerprints. The vault is where the actual file goes — and it is built so the computers holding it cannot read it. Your browser locks the file with a key that never leaves your device, uploads only the scrambled bytes, and the chain records the scrambled file's fingerprint as a key you own and pay rent on. Share the link (the key rides after the #, which browsers never send to a server) or use a passphrase. Stop paying rent and the pointer expires — then the bytes are cleaned up too.

The client seals with AES-256-GCM (WebCrypto in the browser; byte-identical pure Python in pq/aesgcm.py, pinned by the NIST SP 800-38D vectors). The 37-byte PQV1 header — magic, mode, PBKDF2 rounds, salt, IV — is the AEAD's associated data, so it cannot be altered without failing the tag. The file name and type are encrypted inside the ciphertext and the plaintext is zero-padded to a power-of-two bucket (min 1 KiB), so the node learns neither the name nor the exact size. The node stores the blob under cid = SHA3-256(blob), refuses anything without a valid header or whose body reads below 7.5 bits/byte of entropy (an accident guard — no node can prove a blob is encrypted), and keeps it exactly as long as a live chain entry commits to its cid. AES-256 under Grover keeps 128 bits, the same margin as the chain's SHA3-256 commitments; key mode uses a fresh random 256-bit key, passphrase mode PBKDF2-HMAC-SHA256 at 600 000 rounds.

5fStoring smart contracts

A smart contract is a program, and this chain keeps programs the same way it keeps everything else: the program goes into the vault in the open (code nobody can read can't be trusted), and the chain keeps its fingerprint under a name you own — contract/<name>. Anyone can download the code, check it matches the fingerprint, and run it themselves. Upgrading means pointing your name at new code; the chain's history keeps every old version, so nothing is silently replaced. And because the name is a key, you can rent it, sell it, or let it expire.

The contract model is store, don't execute. Code (wasm, Cairo sierra JSON, Cairo source, or any source) is checked for what it claims to be (wasm must start with \0asm, sierra must carry sierra_program) and stored public in the vault under SHA3-256(code); the anchor contract/<name> commits to that hash and inherits every property of a key: an owner, rent, listing and sale. pq_contract show returns the code, recomputes its hash and a Merkle proof to the state root, so a light client can trust it without the store. Contract state lives at contract/<name>/<k>, writable only by the anchor's owner — the chain enforces ownership, not semantics. Execution is off consensus and deterministic: anyone fetches by cid and re-runs. Cairo is the bridge to more: a Cairo execution is what a STARK proves, so a run can be proven and its proof hash anchored next to the code — hash-based, and therefore quantum-safe, end to end. This node stores and verifies code; it does not run contracts in consensus, and does not claim to.

Running it, provably. A wasm contract exporting the pqc1 ABI — pqc_run(state, input) → state, no imports, so no clock, randomness or host call — is a pure function of three byte strings. Its owner runs it on any node and signs a pqr1 receipt {code, state_in, input, state_out, prev} under a dedicated context with their post-quantum wallet, then anchors the receipt's hash at contract/<name>/receipt; receipts chain through prev, so the latest one commits to the whole run log. Verification is refutation: fetch the three blobs by hash, re-run, compare — the chain says who was allowed to append, the wasm says what the append meant. Two examples ship (counter, ledger); the same receipt slot is where a STARK proof hash goes once a Cairo run is proven instead of replayed.

Proof systems. How a transition is accepted off chain is not fixed — each machine declares a proof system: replay (re-execute the code, above), wasm (a custom importless verifier blob exporting the pqp1 ABI, pqp_verify(state_in, input, state_out, proof) → 1/0, that anyone can deploy by hash so the proof carries the work instead of the code), or quorum (k-of-n named post-quantum signers attest the step, nothing executed). The receipt records which system judged it; the console drives the whole flow in WALLET ▸ Machines.

6Consensus, modular

Who gets to add the next block is a swappable part. The chain started with one operator; it can switch to a rotating group, a vote where two-thirds must agree, a vote weighted by how much PQ each validator holds, or proof of work — and switch again later. The switch itself is written into a block and signed by whoever runs the chain at that moment, so history never splits. Every validator signs with a post-quantum key, and they can each pick a different one. VERIFY THE CHAIN still replays everything from the first block, switches included.

An engine answers who proposes at (height, round), what quorum makes a block final, and what else the header must satisfy: authority, roundrobin, bft (> 2/3 voting power), pos (balance weights, SHA3 lottery over the parent hash — no classical VRF), pow (SHA3 hashcash; Grover halves a quantum miner's bits) or a plugin in src/consensus.d/. The schedule of epochs lives in block headers: a migrate field is sealed and committed under the epoch it replaces, so the old consensus authorises the new one, and the replay audit rebuilds the schedule from the log rather than a config file. Seals and votes are signatures under the chain's key types; require_pq demands quantum-safe, many-time validator keys. What is not here: gossip and fork choice — one node, one log. A Merkle proof (pq_prove) takes any key to the state root, which is what a light client needs.

7Units

The money is PQ, and one PQ splits into a billion nq — think dollars and very, very small cents. Write "1.5" in quotes and you mean PQ; write a bare whole number and you mean nq. The system never guesses.

1 PQ = 1e9 nq. In every API, an amount given as a string ("1.5") is PQ, the display unit; a bare integer is nq, the base unit. Nothing is ever guessed from magnitude.

8One surface, three doors

The page you're reading, the API programmers call, and the AI tools all talk to the same functions on one port. Wallets live on the server in a file only its owner can read; the block log is the single source of truth, and any summary derived from it is thrown away the moment the two disagree.

The same functions serve REST under , MCP (35 tools, pq_head through pq_contract) at POST /mcp, and this console. State lives in ~/.mod/postquant: wallet seeds mode 0600 and never committed, blocks.jsonl as the truth, and a state snapshot that is discarded if it ever disagrees with the log.
