# x402 + agents: one namespace of tools and agents

Six kinds of tool share the agent's registry (`src/tools/mod.py`):
builtin, custom, `mod.<name>`, `mcp.<mod>.<tool>`, **`x402.<slug>`** and
**`agent.<name>`**. The model sees one list and can't tell them apart.

## x402.<slug>: a paid API as a tool (`src/tools/x402/mod.py`)

orbit/x402 indexes every x402 (HTTP 402 pay-per-request) service the public
facilitators list. Mounting one turns it into a tool that carries the input
schema the listing publishes (bazaar `queryParams`/`bodyFields`) and states
its price in the description. Calls go through x402's own `x402_call`, so x402
keeps its trust ledger, budget and payment code.

| pay     | what a call does                                                |
|---------|-----------------------------------------------------------------|
| `none`  | default. Unpaid: a 402 comes back as the price, never retried   |
| `auto`  | the node (house) wallet pays, up to `max_price_usd` (default $0.05) |
| `house` | same, house wallet only                                         |

`server=` mounts every service on a paid host or MCP server as
`x402.<server>.<tool>`. State lives off-tree in `~/.mod/agent/x402/mounts.json`.

## x402-<slug>: the same service as an agent

Each mount also creates a **tool-agent**, `agents/x402-<slug>/mod.py`, with
`tool = "x402.<slug>"`. Any agent can be a tool-agent over any tool
(`tool=` on create/update/PUT).

- If the query is a JSON object (or `tool_params`), the tool is called once
  with no model in the loop. `Mod._run_tool_agent` returns a call→finish
  trace, or a single error step when the call fails.
- If the query is prose, the ordinary loop runs with that tool loaded and
  the model works out the arguments.
- A sandboxed (non-host) caller can't reach fleet kinds this way either.

Unmounting removes the tool-agents that wrapped the tool.

## agent.<name>: every agent as a tool (`src/tools/agents/mod.py`)

Any agent can delegate to any other agent with one call, which returns the
agent's answer rather than its trace. A tool-agent's schema is its tool's own
params plus an optional `task`: pass the params and it acts as the tool; pass
a task and it acts as an agent. At most 4 delegated runs can be in flight,
each with a 900s timeout, and every run inherits the caller's key.

## REST

    GET    /tools/x402                 mounted services
    GET    /tools/x402/find?q=&mcp=    search the x402 index (by meaning)
    POST   /tools/x402/mount           owner: {url | server, pay, max_price_usd, agent}
    DELETE /tools/x402/{name}          owner: unmount (+ its tool-agents)
    POST   /tools/x402/{name}/pay      owner: {pay, max_price_usd}
    GET    /tools/agents               every agent as agent.<name>

Mounting is owner-only because the agent reaches x402 over loopback, which
x402 reads as its local owner. A paying mount spends the owner's budget.

## MCP (`src/mcp.py`)

- `agent_x402` with op = list | find | mount | unmount | pay
- every mounted service as its own MCP tool, `x402__<slug>`
- every tool-agent as its own MCP tool, `agent__<name>`, which takes its
  tool's params or a `task`. `AGENT_MCP_AGENTS=all` lists every agent (or
  `none` lists none); `agent_run` reaches any agent either way

The dynamic tools are rebuilt on each `tools/list`, so a new mount or agent
shows up immediately. Calls need a signed-in token and go through the same
`run_tool` gate as REST.
