# leanland

An LLM you read literature with, that leaves *definitions* behind.

You read a paper. You want the thing it describes as something you can run. What
usually happens next is that the same formula gets written three times — once in
a notebook to check it, once in a service to serve it, once in the front end to
show it — and from the day it is written those three copies drift, with nothing
anywhere recording which equation of which paper any of them came from.

leanland inverts that. The formula is written **once**, in a small typed
language, with a citation and with the paper's own numbers attached. Everything
else is *lowered* from it.

```
lit/*.md      the papers — and, more importantly, what you decided about them
lib/*.lean    the definitions — typed, cited, each checked against its source
out/          python · notebooks · a Rust backend · a Next.js surface · Lean 4
```

```
console + API   http://127.0.0.1:50540        (loopback by default)
```

## The one idea

**The library is the source of truth; the code is a shadow of it.**

Three things follow, and they are the whole design:

1. **Codegen is deterministic, not generated by the model.** Every primitive
   carries its Python, Rust and TypeScript emission on the same row of one table
   (`src/ir.py`, `PRIMS`). Adding a primitive is one line and all backends gain
   it at once; there is no way to add it to Python and forget Rust.

2. **The model drafts; the compiler decides.** `elaborate` asks a model for a
   definition, then parses it, typechecks it, and runs the `#example`s the model
   claimed the source states. If any of those fail, *the compiler's error text
   goes back to the model* and it tries again. Nothing reaches `lib/` that did
   not pass all three. An LLM is allowed to draft mathematics; it is never the
   reason mathematics is trusted.

3. **Parity is measured, not assumed.** `m leanland/parity` runs every example
   through the reference interpreter and through every generated target that has
   a toolchain on the box, and reports the worst disagreement. Today, on the
   shipped library: 15 examples, python + rust + js, worst delta `1.1e-16`.

## The language

A deliberately small Lean-flavoured fragment. Not Lean — a mathematician reads
it without a manual and a compiler lowers it without an inference engine.

```lean
/-- Fraction of bankroll to stake on a bet paying `b` to 1 at win probability `p`. -/
@[source kelly1956, eq 1]
def kelly (p : Real) (b : Real) : Real :=
  (p * b - (1 - p)) / b

#example kelly 0.6 1 ≈ 0.2 tol 1e-12
#example kelly 0.5 1 = 0
```

| | |
|---|---|
| types | `Real` `Int` `Nat` `Bool` `Vec Real` `Vec Int`, widening `Nat < Int < Real` |
| forms | `let` (head of a body only) · `if … then … else` · `sum i in a..b, e` · `v[i]` · application by juxtaposition |
| primitives | arithmetic, comparison, logic, `exp log sqrt sin cos tanh abs floor ceil min max`, `len idx vsum mean dot norm` |
| not in it | recursion, loops other than `sum`, state, I/O, integer division |

`div` and `pow` always land in `Real`. Integer division silently disagreeing
between Python and Rust is exactly the class of bug this module exists to stop.

Three rules are enforced rather than suggested:

- **`let` binds only at the head of a body.** That restriction is what lets every
  backend emit a flat prelude instead of growing an expression compiler. Need an
  intermediate inside a loop? Give it its own `def` — naming things is what a
  library is for.
- **Every def is cited or marked.** `@[source kelly1956, eq 1]` points at
  `lit/kelly1956.md`; `@[convention]` says "this is a definition, not a result,
  there is nothing to cite". `verify` lists anything that is neither.
- **Special functions are definitions, not primitives.** There is no `erf`
  primitive, because binding it to `math.erf`, some Rust crate and a JS polyfill
  is three algorithms wearing one name — and parity would then be measuring the
  tolerance instead of the code. `lib/special.lean` writes the cited
  approximation (A&S 26.2.17) once, and it lowers identically everywhere.

## The five targets

| target | what you get |
|---|---|
| `python` | a plain module, plus a pytest file built from the `#example`s |
| `notebook` | one `.ipynb` per def — claim, citation, lean source, code, the paper's numbers, a parameter sweep. Dependencies are inlined, so a notebook can be handed to someone with nothing else |
| `rust` | a **std-only** crate: pure functions, `cargo test` from the examples, and a JSON HTTP backend. No dependencies, so it builds offline and nothing sits between a definition and its endpoint |
| `nextjs` | a TS library, a registry, **one** API route that serves the whole library (`/api/leanland/<name>`), and a page with a form per definition |
| `lean` | real Lean 4, for a toolchain to check if one is installed. Nothing here depends on that |

Everything under `out/` carries a *do-not-edit* banner and is gitignored.
`m leanland/drift` tells you if someone edited one anyway, or if the library has
moved on since the last build.

> The Rust backend is std-only on purpose: this box has no crates registry, and
> a formula should not need a dependency tree to be served. Swapping in axum is a
> `Cargo.toml` line and a rewrite of `src/main.rs`.

## Using it

```bash
m leanland                                  # what is in the library
m leanland/defs                             # every definition, with its citation
m leanland/show kelly                       # one def: source, examples, lowerings
m leanland/verify                           # typecheck + run every #example
m leanland/parity                           # reference vs python vs rust vs js
m leanland/build                            # regenerate out/
m leanland/drift                            # has anyone edited generated code?
m leanland/lower bs_call target=rust        # one def in one language

m leanland/papers                           # the literature
m leanland/arxiv 1706.03762                 # pull metadata off arXiv
m leanland/read kelly1956                   # draft the reading note
m leanland/discuss "why not full Kelly?"
m leanland/elaborate "half-Kelly staking" paper=thorp2006
m leanland/add "@[convention] def double (x : Real) : Real := 2 * x
#example double 2 = 4"

m leanland/serve                            # console + API on :50540
```

The console has four views: **LIBRARY** (browse a def, see it in all four
languages, add one), **LITERATURE** (papers, reading notes, elaborate from one),
**DISCUSS** (chat grounded in your notes and your definitions), **LOWER**
(verify / parity / build / drift).

## The reading side

`discuss` is grounded in `lit/` — your own notes, not the model's recollection —
and in the signatures already defined, so it can point at a definition instead of
restating a formula. It writes nothing.

`read` drafts the reading note for a paper into `lit/<key>.md`, in a fixed shape:
*what it says* / *what I actually want from it* / *caveats worth keeping*. That
third heading is the one that matters — the assumptions that are false in
practice and what breaks when they are. That judgement is the thing being
collected here; the formula is the easy part.

`elaborate` is the gate described above. Try it with `write=0` to see the
proposal and the compiler's verdict without filing anything.

**Providers.** leanland has no API key of its own. It asks the fleet's model
modules in order (`model.openrouter`, `dev`, `agent`) and falls back to calling
OpenRouter directly with the key the box already keeps at
`~/.mod/model/openrouter/apikeys.json`. A module that answers a prompt with its
own info dict is treated as a miss, not as an answer.

## Layout

```
mod.py              the anchor — CLI and fns
config.json         port, fns, targets
src/ir.py           types, expressions, the primitive table, typechecker, reference interpreter
src/lean.py         the surface syntax: .lean text <-> IR
src/lower/emit.py   one IR walk, four emitters (py, rs, ts, js)
src/lower/__init__  the artifacts: python, notebooks, the Rust crate, the Next.js tree, Lean 4
src/library.py      lib/ on disk: load, typecheck, add, build, drift
src/lit.py          lit/ on disk: papers as markdown with front matter
src/chat.py         discuss, read, and the elaborate loop
src/check.py        the parity harness
src/api.py          FastAPI: console + JSON
src/console.html    the zero-dependency console
```

`js` is not a fourth language: it is the TypeScript emitter with the annotations
taken off, reading the same `ts` column of the primitive table. It exists because
the parity harness has to *execute* the web target, and a box with node but no
transpiler cannot execute TypeScript.

## Security

The API binds to `127.0.0.1` and `config.json` sets `route: false`. There is no
auth: an endpoint that edits the library plus half a permission system to guard
it is worse than saying plainly that this listens on loopback. Put it behind the
gateway and the `auth` module before changing either.

## Testing

```bash
python3 -m pytest tests/ -q          # 23 tests
m leanland/test                      # verify + parity, the gate that matters
cd out/rust && cargo test            # the generated crate, against the papers' numbers
cd out/python && python3 -m pytest   # the generated module, same numbers
```

## What is in the library today

14 definitions across 5 papers: Kelly sizing and log growth (Kelly 1956, Thorp
2006), Black–Scholes call/put with `d1`/`d2` (Black & Scholes 1973), the normal
density and CDF (Abramowitz & Stegun 26.2.1 / 26.2.17), and sample statistics
with the population-versus-sample convention pinned down (Sharpe 1994).

They are there as worked examples of the shape a good entry takes — a citation, a
caveat, and a number from the source — not because the library is meant to be
about finance. Add yours and delete these.
